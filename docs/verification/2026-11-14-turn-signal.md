# 방향지시등 판정 보완 및 검증

대상: `feat/drive-experience-refinement`, Pleos Connect 2.1 / Vehicle SDK 2.3.2. 급가속·급감속·제한속도 점수 수식 및 카카오 지도·목적지 내비 연동은 변경하지 않았다.

## 구현 내용

### 좌·우회전

- 콘솔 좌측 −25°에 SDK 원시값 +25°, 우측 +25°에 −25°가 수신되는 것을 확인했다. Pleos 입력을 코어의 좌측 음수·우측 양수 기준으로 변환한다. 원시값은 그대로 보존한다. 이 부호는 현재 환경에서 검증한 계약이며 다른 SDK/실차에서는 재확인해야 한다.
- 핸들만 꺾었다고 회전으로 판단하지 않는다. 최근 10초 이내의 내비 좌/우회전 안내, 안내 지점까지 40m 이내, D 전진 2~25m/s, GPS 진행방향 변화와 실제 이동을 함께 확인한다.
- 회전 시작 조향 5° 이상, 중립 2° 이내, 500ms 이상 조향 증거, 종료 중립 1초를 사용한다. GPS 진행방향 변화 35~135°, 이동 15m 이상, 서로 다른 GPS 관측 3개 이상이 필요하다. 좌표 점프·수신 공백·반대 조향·GPS 품질 부족이면 평가를 보류한다.
- GPS 정확도 10m 및 진행방향 정확도 15° 이내, GPS 나이 1.5초 이내를 요구한다. 조향·깜빡이·비상등은 750ms 이내의 입력만 사용한다. 순서가 뒤집힌 응답과 500ms를 넘긴 조회 응답은 채택하지 않는다.
- 시작 전 3초에서 신호가 500ms 이상 연속 관측되고 시작 1초 이내까지 확인됐는지 검사한다. 캐시를 다시 읽어 지속시간을 만들지 않는다. 관측 시작이 너무 늦어 사전 사용 시간을 알 수 없으면 감점하지 않는다.
- 확인된 정상 사전 사용 0점, 미사용/늦은 사용 −1점, 지속된 반대 방향 −2점, 경기 합계 최대 −10점이다. 회전 후 올바른 신호로 바꿨다고 기존 반대 방향 판정을 지우지 않는다. 짧은 반대 신호 한 번만으로 −2점을 부과하지 않는다.
- 비상등 켜짐·상태 미확인·필수 데이터 누락은 정상으로 간주하지 않고 판단 보류로 남긴다.

이 수치는 앱의 보수적인 프로토타입 판정 기준이다. 법규상의 방향지시등 의무 거리/시간을 검증한 기준은 아니다.

### 차선변경 후보

좌우 S자 조향, 전후 진행방향 안정, 약 2.5~5m 횡이동, 진행방향 복귀, GPS 정확도 1m 이내를 조합해 후보를 기록한다. 가까운 내비 회전 안내가 있으면 후보에서 제외한다.

**차선 존재를 확정하는 기능이 아니며 점수·마일리지에 반영하지 않는다.** 실제 차선변경과 S자 도로/회피 조작을 확실히 구분할 차로 정보가 없다. GPS 정확도 요구가 높아 실제 도로에서는 후보가 잡히지 않을 수 있다.

### 기록·호환

회전 판정, 늦은 사용, 차선변경 후보, 평가 보류 사유를 저장하고 내 기록의 점수 상세에 표시한다. 판정 내역이 없는 경우 정상 사용이 확인됐다는 의미가 아님을 안내한다. 새 판정 버전은 `distance-bonus-longitudinal-v2-turn-v2`이며 기존 v1/구형 기록의 점수와 산식 설명은 유지한다.

## 콘솔과 에뮬레이터 검증 범위

`scripts/verify-turn-console.ps1`은 로컬 Virtual Console에 입력하고 앱의 실제 `PleosConnection` → `ManeuverMonitor`를 사용한다. 기어·속도·조향·방향지시등·비상등은 실제 SDK 수신값이다. **GPS 경로와 내비 회전 안내만 테스트 경로로 대체했다. 전체 실시간 내비 경기 검증과 구분해야 한다.** 진단은 경기를 시작하거나 실제 기록·보상을 생성하지 않는다.

| 시나리오 | 확인 결과 |
|---|---|
| 좌회전 + 사전 좌측 신호 | 정상 일치, 감점 0 |
| 우회전 + 사전 우측 신호 | 정상 일치, 감점 0 |
| 좌회전 + 신호 끔 | 미사용, −1 |
| 좌회전 + 사전 우측 신호 | 반대 방향, −2 |
| 좌회전 시작 뒤 좌측 신호 | 늦은 사용, −1 |
| 비상등 켜짐 | 판단 보류, 감점 없음 |
| GPS 누락 | 후보 생성 안 함, GPS 부족 기록, 감점 없음 |
| 좌측 S자 조향 + 모의 정밀 경로 | 차선변경 후보, 감점 0 |
| 우측 S자 조향 + 모의 정밀 경로 | 차선변경 후보, 감점 0 |

첫 전체 실행에서 우측 차선변경 후보가 누락됐고, 분리 재실행에서는 양쪽 모두 통과했다. 이후 반복·지연 검사에서 테스트의 관측 중단으로 동일한 누락을 재현했다. 아래 추가 조사 결과를 참고한다. 실도로 정확도 검증 완료로 취급하지 않으며 관찰 전용을 유지한다.

비상등 테스트 중 콘솔에서 방향지시등을 설정하면 비상등이 꺼지는 상호 배타 동작을 확인했다. 재현 스크립트는 방향지시등을 설정한 뒤 비상등을 설정한다. 테스트 종료 시 P·0km/h로 되돌리고 기존 조향·깜빡이·비상등 상태를 복원한다.

로그: `android/app/build/turn-console-replay-first.log`(7개 회전/보류 시나리오와 첫 후보 검사), `turn-console-replay.log`(후보 재검사). 빌드 산출물은 Git에 포함하지 않는다.

## 남은 검증과 다음 단계

### 자동 검증 결과

- 코어 단위 테스트 **163개**, 앱 단위 테스트 **41개** 통과. 조향 부호, 늦은 신호, 반대 신호 지속시간, GPS 위치 점프, 불충분한 사전 관측, 비상등/누락/캐시, 차선변경 후보·곡선·역주행 제외를 포함한다.
- 에뮬레이터 계측 검사 **29개 최종 통과**: 기존 점수의 결과/배지/보상 연결 6개, 기록 저장 6개, 구버전 저장 호환 2개, 안전벨트 세션 9개, 좌석 어댑터 4개, 상세 화면 2개. 첫 실행은 새 저장 테스트의 버전 표기를 구형으로 잘못 넣어 1개 실패했다. 실제 새 버전에 맞춰 테스트 데이터를 고친 뒤 저장 검사 6개를 재실행해 모두 통과했다. 제품의 구버전 저장 규칙은 바꾸지 않았다.
- 앱/계측 APK 빌드 성공, 현재 브랜치 APK 설치 완료. 앞 표의 콘솔 검사는 위 29개와 별도로 수행했다.
- 독립 코드 검토에서 기록 시작 직후 사전 신호 이력이 부족한데 늦은 사용으로 감점하는 사례를 발견했다. 먼저 실패하는 회귀 테스트로 재현한 뒤 판단 보류로 수정했다.

검증 로그는 `android/app/build/turn-final-build.log`, `turn-final-ui-build.log`, `turn-integration-tests.log`, `turn-persistence-final.log`에 남겼다. 첫 통합 로그에 남은 실패는 마지막 저장 검사 로그와 함께 확인한다.

### 실도로 검증

1. 실제 GPS와 내비 안내를 사용한 좌/우회전, 곡선 도로, 연속 교차로, 평행/겹치는 도로에서 오감점 확인.
2. 기록 시작 직후 회전, 자동 깜빡이 취소, 비상등 전환, 통신 지연을 실차/개발용 이미지에서 반복 점검.
3. 전체 경기 → 결과 → 내 기록 → 보상 흐름을 실제 차량 신호로 연속 검증. 현재 이미지의 운전석 벨트 체결 원시값을 착용으로 조작하지 못하는 기존 제약이 있어, 이번 진단은 벨트 실격 경로와 분리해 실행했다. 제품의 벨트 조건을 우회하거나 완화하지 않았다.
4. 차선변경은 후보 검출 안정성 및 도로/차로 정보 확보 후 채점 적용 여부를 결정한다. 정확한 차선변경 인식이나 굽은 도로 오인 방지가 완성됐다고 발표하면 안 된다.

## 추가 조사: 차선변경 후보 누락과 콘솔 응답 대기

### 재현한 원인

이전 계측 테스트는 `command()`에서 콘솔 조작이 SDK에 반영될 때까지 기다렸고, 그동안 `ManeuverMonitor`에 관측값을 전달하지 않았다. 판정기는 최근 2.5초 안에 1.75초 이상의 직진 증거를 요구하므로 이 공백이 커지면 후보를 시작하지 않는 것이 정상이다. 우측만의 부호 오류는 발견하지 않았다.

1. 수정 전 일반 조건에서 좌 4회·우 4회 모두 통과.
2. 콘솔 조작에 600ms 지연을 추가하자 좌·우 모두 누락 재현.
3. 좌측 관측 간격은 **1,277ms**, 최근 직진 증거는 **1,010ms**였다. 우측은 각각 **1,183ms / 1,265ms**였다. 둘 다 필요한 직진 증거 1,750ms보다 짧았다.
4. 실패 시 실제 SDK는 D·약 8.33m/s·신호 OFF·비상등 OFF·좌/우 −8°/+8°를 정상 전달했다. GPS는 이전과 같은 모의 정밀 경로였다. 입력 방향 오류가 아니라 테스트가 샘플을 판정기로 보내지 않는 공백으로 설명되는 실패였다.

최초 누락 1건에는 개별 관측 시점 로그가 없으므로 그 실행까지 같은 원인이라고 단정할 수는 없다. 이번에는 동일 증상을 양방향으로 재현하고 공백 수치를 확인한 뒤 수정했다.

### 수정 범위

- 콘솔 응답 대기 중에도 약 200~400ms 간격으로 실제 SDK 관측을 판정기에 계속 전달한다. SDK 값을 임의로 채우지 않는다.
- 모의 GPS의 전진 거리는 경과시간에 맞춰 진행시킨다. 명령 응답 시간만큼 GPS 재생까지 멈추던 문제를 함께 제거했다.
- 좌우 반복 횟수와 지연 주입 옵션, 명령 대기시간/첫 조향 전 증거/최대 관측 간격 로그를 추가했다. 매 실행 로그를 다른 파일에 보관한다.
- **제품의 후보 판정 조건, 조향 기준, 점수 로직은 이번 조사에서 변경하지 않았다. 차선변경 후보 감점은 항상 0점이다.** 실제 데이터가 부족하면 계속 후보를 만들지 않는다.

### 검증

- 수정 후 600ms 지연 조건에서 좌 3회·우 3회 **6/6 통과**, 최대 관측 간격 354~392ms. 각 후보의 방향·종류·감점 0을 검사했다.
- 코어 전체 **165개 통과**. 이번에 추가한 두 회귀 검사는 관측 공백이 있으면 후보를 만들지 않고, 대기 중 직진 관측을 계속 공급하면 좌우 후보 모두 감점 0으로 남는지 확인한다.
- 수정 후 일반 조건도 좌 3회·우 3회 **6/6 통과**, 최대 관측 간격 295~366ms. 지연 조건과 합해 **12/12 통과**했으며 모두 감점 0점이었다.

```powershell
./scripts/verify-turn-console.ps1 -Case lanes -Repetitions 3
./scripts/verify-turn-console.ps1 -Case lanes -Repetitions 3 -CommandDelayMs 600
```

## 추가 재시도: 긴 응답 대기와 신호 수신 간격 (2026-11-14)

### 콘솔 대기 개선 및 재검증

- 명령당 SDK 반영을 최대 **30초** 기다리며, 기다리는 동안에도 관측과 콘솔 연결 유지 요청을 계속한다. 실행 옵션으로 최대 60초까지 설정할 수 있다.
- 첫 조향 명령을 의도적으로 **6초 늦춘** 좌우 각 2회 검사에서 **4/4 통과**했다. 실제 명령 대기는 6,325~6,569ms였지만 관측 간격은 최대 363~387ms로 유지됐다. 모든 차선변경 후보는 감점 0이다.
- 준비 조건에 SDK의 실제 D·30km/h 수신 여부를 추가했다. 조향만 반영되고 차량은 정지 상태인 검사를 정상 재현으로 세지 않는다.
- 회전 검사도 명령 대기 중 관측을 계속하고, 실패 시 개별 입력 전체를 로그에 남기며 나머지 사례까지 실행하도록 보완했다.

### 재시도 중 발견한 실제 오판정과 수정

`turn-console-all-20261114-131202.log`에서 우측 신호를 계속 켰는데 `LATE`로 판정됐다. 실제 수신 시각 간격이 504ms, 508ms로 늘어났을 때 기존 500ms 연속성 조건이 신호 유지 이력을 끊었다. 이는 운전자의 늦은 조작이라는 근거가 아니다.

- 수신 간격 허용값을 개별 데이터의 기존 신선도 기준인 **750ms**에 맞췄다. 사전 신호 유지 요건 **500ms**는 그대로다.
- 750ms를 넘는 관측 공백은 늦은 사용으로 감점하지 않고 판단을 보류한다.
- 실제 시간 간격을 재현한 테스트와 신선도 초과 공백 테스트가 수정 전 실패하고 수정 후 통과함을 확인했다.

### 실제 GPS·내비 수신을 60초 기다린 결과

`turn-console-live-inputs-20261114-131806.log`는 GPS나 회전 안내를 대체하지 않은 진단이다. 앱의 위치 권한이 사용 중 허용이므로, 화면이 없는 최초 진단 대신 실제 Activity를 띄워 다시 실행했다. D·30km/h가 SDK에 전달된 것을 확인한 후 60초 동안 240개 표본을 수집했다.

- 240개 모두 실제 D·약 8.33m/s를 수신했다.
- 240개 모두 GPS 위치 오차 **5m**, 방향 오차 **30°**였다. 회전 판단은 방향 오차 15° 이하가 필요하므로 모두 `GPS_UNAVAILABLE`로 보류됐다. 차선변경 후보는 위치 오차 1m 이하도 요구하므로 이 값으로 검증할 수 없다.
- 내비 상태는 목적지 수신·0m였고, 240개 모두 좌/우회전 안내가 없었다. 활성 경로의 교차로 안내 수신을 검증한 결과가 아니다.
- 이벤트와 감점은 없었다. 계측 테스트 성공은 **수신 진단을 완료했다**는 의미이며 실제 GPS로 좌우회전을 검증했다는 의미가 아니다.
- 종료 후 콘솔의 P·0km/h를 확인하고 메인 앱을 다시 열었다.

남은 조건은 충분한 정확도의 GPS 이동 경로와 활성 내비의 회전 안내를 함께 공급하는 것이다. 콘솔 기능 목록에는 GPS 경로·방향 정확도·내비 회전 안내 조작 기능이 없으며, 더 오래 기다리는 것만으로 위 품질 값이 개선되지는 않았다. 실제 경로를 재현할 수 있는 개발 환경 또는 실차에서 곡선·평행 도로·연속 교차로를 검증해야 한다. 전체 경기 검증에는 기존 운전석 벨트 체결값 조작 제약도 별도로 남는다. 이 검사를 통과시키기 위해 GPS 기준이나 벨트 조건을 완화하지 않았다.

## 가상 GPS → 내장 내비 연결 재시도 (2026-11-14 13:25 이후)

**최종 목표인 실제 내비 안내에 따른 좌·우회전 / 깜빡이 켬·끔 비교는 아직 미완료다.** 이번에는 판정기에 GPS나 안내를 직접 대입하지 않고, Android GPS 입력과 설치된 내비 앱의 실제 응답을 대조했다. 제품 코드나 채점 기준은 변경하지 않았다.

### 성공한 연결

1. `adb emu geo fix`로 에뮬레이터 GPS 위치를 변경했고, Android LocationManager에서 변경된 좌표를 확인했다.
2. 기존 경로 요청 기능으로 내장 내비에 여의도한강공원 목적지를 보냈다. 내비 경로 생성과 목적지 수신 테스트가 통과했다(`live-route-start.log`). 실제 화면에 경로와 안내 종료 버튼도 나타났다.
3. 실제 NaviHelper의 `onTBTInfo()`에서 `TURN_RIGHT / 700m / 대왕판교IC 방면` 등을 수신했다. 우리 앱도 `RIGHT / 700m`로 읽었다. 이번 회전 안내는 테스트가 만들어 넣은 값이 아니다.
4. 테스트에 한해 mock-location 권한을 허용하고 Android GPS test provider를 사용했다. 0.5m 위치 오차·2° 방향 오차를 가진 좌표가 우리 앱과 Pleos FusedLocation 서비스까지 전달됐다. 60초 검사 중 좌표를 두 지점으로 변경한 것도 양쪽에서 확인했다.

### 확인된 차단 지점

| 입력 / 관찰 경로 | 결과 |
|---|---|
| Android GPS | 주입한 `(37.4981, 127.0631)` 수신 |
| Android GPS test provider | 이후 `(37.4991, 127.0631)`로 변경됨 |
| Pleos FusedLocation 서비스 로그 | 위 두 위치의 콜백 수신 |
| 실제 내비 `getCurrentLocationInfo()` | 계속 `(37.4127212, 127.094681)` / 수정구 시흥동 |
| 내비의 첫 회전 안내 | 계속 우회전 700m |
| 내비 로그 | `GpsLocationSource: Invalid NMEA message`, `NMEA checksum mismatch` 반복 |

내비는 GPS 원문(NMEA)의 체크섬이 맞지 않는 문장을 거부하고 있었다. 기본 위치 입력이 생성한 문장은 내용이 바뀌어도 끝의 체크섬이 `*47`로 고정돼 있었다. 이 현상은 실행 중인 내비 로그와 Android NMEA 리스너 양쪽에서 확인했다. [AOSP 에뮬레이터 GPS 소스](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-35-1-release/android/emu/gps/src/android/gps.cpp)에도 해당 고정 체크섬 생성 코드가 있다. 이 소스가 설치 버전과 완전히 동일하다는 의미는 아니며, 설치 환경의 관찰 증거는 로그다.

### 우회 방법도 재시도한 결과

- 매 문장마다 체크섬을 올바르게 계산한 GPGGA/GPRMC를 `geo nmea`로 반복 전송했다.
- ADB 전송과 공식 로컬 에뮬레이터 콘솔 TCP 직접 연결을 모두 시도했다. 콘솔 명령 응답은 OK였다.
- 그러나 Android NMEA 리스너에 수신된 문장은 계속 기본 입력의 정수 초 시각 / 위성 6개 / 고정 `*47` 형식이었다. 직접 보낸 소수 초 시각 / 위성 10개 형식은 최종 20초 진단에서 관찰되지 않았다. 명령 수락을 실제 기기 수신 성공으로 취급하면 안 된다.
- 내비를 전면에 둔 상태에서도 재시도했지만 위치와 회전 거리가 갱신되지 않았다.
- test provider는 앱 위치 검증에는 사용할 수 있지만, 이번 내비의 GPS 원문 수신을 대체하지 못했다. 이것만으로 실제 내비까지 연결됐다고 주장할 수 없다.

### 재현 자료와 다음 조건

`NavigationGpsIntegrationTest`는 명시적으로 `liveGps=true`를 지정해야 실행된다. 위치 수신·내비 위치·회전 안내·NMEA 원문을 기록하고, 앱과 내비가 같은 위치를 받지 못하면 실패하도록 했다. 초기 탐색 로그의 `OK (1 test)`는 탐색 루틴 종료만 의미했으므로 최종 검사에는 위치 일치 검증을 추가했다.

```powershell
./scripts/verify-native-gps.ps1 -Seconds 20 -CancelRouteOnFinish
```

로그는 `android/app/build/`에 남는다.

- `nav-gps-native.log`: 기본 GPS와 내비 위치 불일치, 실제 TBT 수신.
- `nav-gps-mock.log`: Android test provider 60초, 두 위치 주입; 내비 위치 미갱신.
- `native-gps-20261114-133857.log`: 정상 체크섬 원문 ADB 반복 전송 대조.
- `native-gps-20261114-134034.log`: TCP 직접 전송 대조.
- `native-gps-20261114-134441.log`: 위치 일치를 필수로 검증하는 최종 실행.
- `nav-gps-final-build.log`: 진단 계측 APK 빌드 성공.

최종 실행은 예상한 연결 실패를 실제로 검출했다: **위치 일치 표본 0개**, 수신 NMEA **44개 중 체크섬 정상 2개**, `Android GPS and built-in navigation did not share the injected position` 단언 실패. 기본 문장의 체크섬이 우연히 맞는 일부 시점이 있어도 정상적인 위치 연동이나 경로 재생 성공을 의미하지 않는다. 가상 위치 권한은 `default`로 복원됐음을 확인했고, test provider를 제거했다. 제가 시작한 내비 경로는 종료 요청을 보냈으며, 에뮬레이터 좌표는 검사 전 위치로 되돌리고 메인 앱을 다시 열었다.

필요한 것은 이 Pleos 이미지에서 **정상 NMEA가 내비까지 전달되는 GPS 재생 방법 또는 이를 수정한 에뮬레이터 구성**이다. Pleos 측에는 위 좌표 불일치, NMEA 체크섬 오류, `geo nmea` OK에도 직접 보낸 원문이 관찰되지 않는 재현을 전달하면 된다. 이를 해결한 다음 동일한 좌우 도로 경로를 두 번씩 재생해 깜빡이 켬/끔 판정을 비교해야 한다. 이번 결과를 앞 절의 모의 GPS·모의 안내 13개 통과 결과와 혼동하지 않는다. 차선변경은 감점 0의 관찰 전용을 그대로 유지했다.
